## 1. 하드웨어 브링업 결과 (2026-08-24)

### 1.1 확정 ✅

| 항목 | 결과 |
|---|---|
| JTAG / SRAM 로드 | `openFPGALoader --detect` 인식, `make program` 성공 |
| LED0 하트비트, BTN0→LED2, BTN4→LED3(FREERUN) | 전부 정상 |
| **SDCLK E15 = 1.65V** | 스캔 클럭 토글 중 |
| **GDCLK A15 = 3.05V** | 사양 일치 |
| **SDCE0 B13 = 0.296V** | 사양 일치 (91% Low) |
| GDCLK/SDLE 카운터 | fail 코드가 **3**이라는 것 = 두 카운터 모두 **정확히 1927** |
| **SDCE0 active_cnt** | 스캔 OFF로 얼린 값 **0x90000**(589,824) — 프레임 ~96% 지점. 카운팅 자체는 건강 |

> ⚠️ 첫날 B13=3.3V / A15=0V 측정치는 **프로브 착오**(재측정으로 반박됨).
> 인접 핀 GDOE/SDOE는 구동 중 상시 High(3.3V)가 정상. 헤더 프로빙 시 실크 재확인할 것.

### 1.2 해결 — fail 코드 3의 진짜 원인 (파라미터 폭 절단)

**스캔은 정상이었다. 기대값이 0이었다.**

```verilog
`define DEFAULT_HACT 12'd320
`define DEFAULT_VACT 12'd1920
.EXP_ACTIVE(`DEFAULT_HACT * `DEFAULT_VACT)   // top.v -- 12비트로 잘림
```

Verilog에서 곱셈 결과 폭은 피연산자 최대 폭이다. 둘 다 12비트라 결과도 12비트로
잘리는데, `320 * 1920 = 614400 = 4096 * 150`이라 **나머지가 정확히 0**이다.

| 툴 | 평가 결과 |
|---|---|
| iverilog | 32비트 정수 문맥으로 승격 → 614400 → **시뮬 통과** |
| yosys | 규칙대로 절단 → **0** → `active_cnt != 0` 항상 참 → **실물 fail 3** |

`EXP_VTOTAL`(1927)은 12비트에 들어가 안 잘렸다. **그래서 GDCLK/SDLE만 맞고
SDCE0만 틀리는** 정확히 그 증상이 나왔다.

UART 한 줄이 이걸 즉시 드러냈다 — `E=+096000`, 즉 오차가 기대값 전체와 같았다.

**수정**: `defines.vh`에 폭을 미리 넓힌 `DEFAULT_VTOTAL` / `DEFAULT_ACTIVE`를 두고
`top.v`·`tb_top.v`가 공유. 점에서 곱하지 말 것. yosys 재확인 `32'd614400`, 실물
재확인 `E=+000000 P=1 F=0`.

> ⚠️ 파라미터 오버라이드에는 정수 문맥이 생기지 않아 `localparam integer` 트릭이
> 안 먹힌다. `tb_top.v`에는 이 함정을 경고하는 주석이 이미 있었는데 `top.v`에는
> 적용돼 있지 않았다. 앞으로 사이즈드 리터럴끼리 곱하는 자리는 전부 의심할 것.

> ⚠️ 이전 세션의 `active_cnt = 0x90000` 판독은 **성립하지 않는다**. 당시
> `nib_idx`가 2비트라 21비트 카운터의 하위 16비트만 보였고(0x96000의 상위 니블
> `9`는 표시 불가), LED 극성도 뒤집혀 읽혔다. 정상값 (idx3, 니블 6)이
> (idx0, 9)로 보이는 조합이었다.

### 1.3 UART 디버그 콘솔 (신규 — 주력 진단 수단)

Tang Primer 20K **Dock**의 FT2232는 2채널이고, 채널 B가 FPGA **M11**에 이미
배선돼 있다. **추가 배선 없이** 기존 USB 케이블 그대로 쓴다.

| 포트 | 용도 |
|---|---|
| `/dev/cu.usbserial-1100` | JTAG (openFPGALoader) |
| `/dev/cu.usbserial-1101` | **UART 콘솔** |

프레임마다(기본 15프레임에 1회 = 초당 4줄) 한 줄이 나온다:

```
G=787 S=787 A=096000 E=+000000 P=1 F=0
│     │     │        │         │   └ fail_code
│     │     │        │         └───── pass
│     │     │        └─────────────── active_cnt - 기대값, 부호+절대값
│     │     └──────────────────────── SDCE0 액티브 사이클
│     └────────────────────────────── SDLE 상승 에지
└──────────────────────────────────── GDCLK 상승 에지
```

전부 16진. 정상 = `G=787 S=787 A=096000 E=+000000 P=1 F=0`.
값이 16비트를 넘으면 포화(`7fffff`/`800000`)시켜, 랩어라운드된 값이 작은 오차처럼
보이는 일이 없게 했다.

읽는 법:
- `E=+000000` → 카운트 정확
- 320의 배수(`±000140` 등) → **라인 단위** 누락/초과 (320 = HACT)
- 320의 배수가 아님 → 라인 내부에서 어긋남 (클럭 인에이블/CDC 의심)
- 줄마다 값이 흔들림 → 과도기가 아니라 불안정 (신호 무결성)

**BTN0을 눌러 스캔이 돌아야 줄이 나온다.** 스캔이 멈춰 있으면 GDSP가 토글하지
않아 프레임 펄스가 없다. 한 줄도 안 나오는 것 자체가 정보다.

관련 RTL: `rtl/uart_tx.v`(8N1 송신기), `rtl/debug_uart.v`(포매터),
`epd_selftest.v`의 `frame_done` + 래치 출력 포트.

### 1.4 UART 받는 법 (중요)

보드를 다시 꽂을 때마다 `/dev/cu.usbserial-1101`의 termios가 **9600으로
리셋**된다. `stty`로 잡아도 포트를 닫는 순간 날아가므로 소용없다.
**포트를 연 채로 보율을 설정해야 한다.**

```bash
python3 - <<'EOF'
import serial, time
s = serial.Serial('/dev/cu.usbserial-1101', 115200, timeout=0.2)
s.reset_input_buffer()
end = time.time() + 10
while time.time() < end:
    d = s.read(4096)
    if d: print(d.decode('ascii','replace'), end='')
EOF
```

`cat /dev/cu.usbserial-1101` 로 받으면 글자가 깨진다 — 이 함정에 한 번 빠졌다.

### 1.5 SD 데이터 버스 검증 (`rtl/epd_sd_check.v`)

`epd_selftest.v`는 제어신호 에지만 세고 SD 버스에 실린 것은 보지 않는다.
그 구멍을 메운다. 액티브 윈도우 동안 프레임마다:

| UART 필드 | 검사 | 실측 |
|---|---|---|
| `U` | `SD[15:8]`의 프레임 OR | **`ff`** |
| `Z` | `2'b11`(Hi-Z)이 실린 사이클 수 | **`0000`** |
| `D` | 가로 2배 확대 배선 불변식 위반 사이클 수 | **`0000`** |

**`U=ff`가 plan.md §7.4가 요구한 16비트 전환의 증거다.** 8비트 모드에서는 caster가
`{8'd0, pixel}`을 내보내므로 `U=00`이 나온다. 나아가 `ff`는 상위 4개 필드에서 두
비트가 모두 선 적이 있다는 뜻이라 VPOS(`2'b10`)·VNEG(`2'b01`)가 둘 다 출력되고
있음을 말한다 — 한 극성으로만 구동되는 상태가 아니다.

**`D`는 멀티미터로 불가능한 검사다.** caster는 `{p3,p3, p2,p2, p1,p1, p0,p0}`로 각
코어 픽셀을 복제해 내보내므로 인접 2비트 필드쌍은 매 사이클 같아야 한다. 상위
바이트에서 선이 바뀌어 물렸거나 쇼트가 나면 `U`가 멀쩡해도 여기서 잡힌다.
프레임당 614,400 사이클 × 4개 쌍 전부 무결.

카운터는 16비트에서 포화시켰다 — 랩된 값이 작은 오차로 보이면 안 된다.

### 1.6 세로 2배 확대 검증 (`rtl/epd_line_dup.v`)

`epd_sd_check`는 한 워드 안만 본다. 세로 2배는 라인을 가로지르는 성질이라 거기서
보이지 않는다. caster의 세로 확대는 라인버퍼다:

```verilog
// 짝수 라인: 파이프라인 값을 출력하면서 라인버퍼에 저장
if (scan_in_hact && (v_cnt_offset[0] == 1'b0)) scale_line_buf[scale_ptr] <= current_pixel;
// 홀수 라인: 라인버퍼에서 되읽음 (+1은 레지스터 1단 지연 보정)
odd_line_pixel <= scale_line_buf[scale_ptr + 10'd1];
epd_out_pixel = (v_cnt_offset[0] == 1'b1) ? odd_line_pixel : current_pixel;
```

**따라서 홀수 라인은 바로 앞 짝수 라인을 워드 단위로 그대로 반복해야 한다.**
이건 버스에 나타나는 성질이므로 패널 없이, 그림이 뭔지 몰라도 검사할 수 있다.

라인마다 액티브 워드를 CRC-32 다항식(`0x04C11DB7`)으로 접어 서명을 만들고,
짝수 라인에서 보관했다가 홀수 라인에서 비교한다. 단순 XOR이면 두 워드가 자리를
바꿔도 못 잡지만 CRC는 순서까지 본다.

| UART 필드 | 의미 | 실측 |
|---|---|---|
| `V` | 서명이 어긋난 라인 쌍 수 | **`0000`** |
| `L` | 비교한 라인 쌍 수 | **`03c0`** = 960 |

**`L=03c0`은 그 자체가 검사다.** 패널 1920라인 = 960쌍인데 모자라면, GDCLK가
여전히 1927을 세는데도 데이터 라인이 빠지고 있다는 뜻이다. 제어신호 카운트만으로는
절대 안 잡히는 결함이다.

**`V`가 세로 2배의 유일한 직접 증거다.** 라인버퍼·읽기 포인터·`+1` 지연 보정
어느 하나라도 틀리면 960쌍이 전부 불일치로 터진다. 과거 "세로 확대 라인버퍼의
1워드 어긋남"으로 기록된 버그가 정확히 이 종류이고, 이런 결함은 제어신호가 전부
완벽해 보이는 채로 화면만 세로로 찌그러지거나 찢어지게 만든다.

> 설계 주의: 블랭킹 라인이 패리티 슬롯을 먹지 않도록 `had_data` 게이트를 뒀다.
> 이게 없으면 첫 쌍 이후 계속 짝수 라인끼리 비교하게 된다.

> `D`를 인접 쌍(`f7==f6`, `f5==f4`, ...)으로 잡은 것도 의도적이다. `vin.v`가
> `{shade,shade,shade,shade}`를 내보내므로 "네 필드 전부 같아야 한다"로 잡고
> 싶어지지만, 디더링은 픽셀 위치마다 다르게 작동해서 같은 계조라도 중간톤에서
> 2비트 출력이 갈린다. 인접 쌍 등식은 배선 복제에서 나오는 성질이라 계조와
> 무관하게 항상 참이다.

### 1.7 프레임 레이트 · 클럭 절대 주파수 실측

카운트는 전부 클럭 사이클 수라, 맞다는 것은 **비율**이 맞다는 뜻이지 절대 주파수
증거가 아니다(20 MHz여도 1927/614400은 똑같이 센다). UART 라인 레이트로 잰다.

20초 클린 윈도우 (버퍼를 3초간 강제로 비운 뒤 측정):

| | |
|---|---|
| 라인 | 80 (3.997 lines/s, DECIMATE=15) |
| 프레임 | 1200 → **59.96 fps** (설계값 60.00) |
| 역산 클럭 | **40.472 MHz** (공칭 40.5) |
| 편차 | **−0.07 %** — 호스트 타이밍 오차 수준 |
| 서로 다른 라인 | **1개** — 1200프레임 전부 동일, 지터 없음 |

rPLL 27 MHz × 3/2 가 실제로 나오고 있다. 측정 스크립트는 §1.4 방식과 동일하게
포트를 연 채로 보율을 잡아야 한다.

### 1.8 패턴·모드 전수 순회 (2026-08-24)

120초 타임스탬프 로그를 걸어두고 BTN2 4회(패턴 0→1→2→3→0), BTN3 4회
(모드 0→1→2→3→0)를 눌렀다. **480줄 수집.**

**불변식 위반 0건.** 전 구간에서 다음이 고정:

```
G=787 S=787 A=096000 E=+000000 P=1 F=0 Z=0000 D=0000 V=0000 L=03c0
```

| 확인된 것 | 의미 |
|---|---|
| `D=0000` 유지 | 계조 램프에서 디더링이 픽셀마다 다른 값을 만들어도 가로 2배 복제는 안 깨진다 |
| `L=03c0`·`A=096000` 유지 | 패턴 2(버스 최고속 토글)와 FAST_GREY(부하 최대)에서도 라인 유실·언더런 없음 |
| `V=0000` 유지 | 세로 2배도 내용과 무관 |

`U`만 움직였고, 변화가 **정확히 8건** — 누른 횟수와 일치한다:

| 시각 | `U` | 대응 |
|---|---|---|
| 0.1~24.6 | `ff` | 패턴 0 (애니메이션이라 계속 구동) |
| 24.8 | `ff`→`f0` | BTN2 ① |
| 36.3 | `f0`→`00` | BTN2 ② |
| 59.0 | `00`→`ff` | BTN2 ③ |
| 69.3 | 순간 `00` | BTN2 ④ (패턴 0 복귀) |
| 81.3 | 순간 `00` | BTN3 ① NO_DITHER |
| 88.8 | 순간 `00` | BTN3 ② BLUE_NOISE |
| **99.3** | **`55`** | **BTN3 ③ FAST_GREY** |
| 111.3 | 순간 `00` | BTN3 ④ BAYER 복귀 |

**`U=55` = `01 01 01 01`, 네 필드 전부 VNEG.** 다른 모드에서 한 번도 안 나온
고유 서명이라, 모드 전환이 `csr_master`를 거쳐 caster까지 도달해 구동 방식을
실제로 바꿨다는 증거다. 버튼이나 LED가 아니라 출력 버스에서 확인됐다.

관측된 모든 `U` 값(`ff` `f0` `55` `00`)이 복제 구조를 지킨다 — 상위 두 필드는
`p3`의 복제, 하위 두 필드는 `p2`의 복제. `D=0000`과 독립적으로 일치한다.

> ⚠️ 위 대응은 8개 이벤트와 8번의 누름을 순서대로 맞춘 **추론**이다.
> 구간별 패턴 확정은 UART에 `N=`/`M=` 필드를 실은 빌드로 해야 한다
> (RTL 작성·포맷 검증 완료, 미빌드).

### 1.9 검사 판정 통합 (`rtl/epd_verdict.v`)

검사가 세 모듈로 흩어져 있고 전부 UART로만 보고했다. 노트북을 붙여둔 책상에서는
괜찮지만 벤치에서는, 또 보드가 케이스에 들어가면 쓸모가 없다. LED1 하나로 접었다.

| LED1 | 원인 | 출처 |
|---|---|---|
| 계속 켜짐 | 전부 정상 | |
| 1회 깜빡 | GDCLK | `epd_selftest` |
| 2회 깜빡 | SDLE | `epd_selftest` |
| 3회 깜빡 | SDCE0 | `epd_selftest` |
| 4회 깜빡 | Hi-Z 또는 가로 2배 복제 | `epd_sd_check` |
| 5회 깜빡 | 쌍 불일치 또는 쌍 개수 | `epd_line_dup` |

**심각도가 아니라 계층 순서로 우선순위를 뒀다.** 스캔이 깨지면 이후 검사는 전부
무의미하므로, 가장 앞에서 틀린 것이 보고할 가치가 있는 것이다.

깜빡임 슬롯 8→16(4초 주기). 기존 8슬롯은 3회까지만 표현 가능하고 5회는 10슬롯과
간격이 필요하다. `sd_or`는 판정에서 뺐다 — 구동 여부는 Caster가 목표 도달 시
멈추는 정상 동작이라 실패가 아니다.

### 1.10 시뮬용 DDR3 메모리 모델 (`mig_wrapper.v`)

기존 스텁은 **128비트 레지스터 하나로 주소를 무시**했다. 모든 픽셀이 같은 상태
워드를 읽으니 화면 전체가 한 덩어리로 안정되거나 안정되지 않았고, 파이프라인
하류가 전부 시뮬에서 검증 불가능했다 — 계조, 웨이브폼 진행, 애초에 그림이 맞는
그림인지까지.

`SIMULATION` 분기에 실제 배열을 넣었다. `memif.v` 구동 방식대로 모델링:
`instr` 000 쓰기 / 001 읽기, 버스트 16워드, 쓰기는 FIFO 선충전 후 커맨드, 읽기는
커맨드 후 pop, 읽기 FIFO는 first-word fall-through. `memif`가 실제로 읽는 상태
신호는 `cmd_full`·`wr_full`·`rd_empty` 셋뿐이다(나머지는 그쪽에 unused 표시).

**합성 경로는 스텁 그대로다.** 2.34 MB는 GW2A-18의 약 103 KB BSRAM에 안 들어간다.
하드웨어는 Gowin DDR3 IP가 필요하지만(plan.md 2-2), 시뮬레이션에는 그 제약이 없어
IP가 생기기 전에 로직을 완성·검증할 수 있다.

효과가 즉시 나타났다:

```
스텁     sd_check: U=00     화면 전체가 한꺼번에 안정 → 무구동
메모리   sd_check: U=55     픽셀이 계속 제대로 구동됨 (01 = VNEG)
```

시뮬 결과 (양쪽 PASS):
```
selftest latched: gdclk=1927 sdle=1927 active=614400 err=0
sd_check: U=55 Z=0 D=0
line_dup: V=0 L=960
verdict: pass=1 fail_code=0
```

### 1.12 `make demo`(PANEL_TEST) 시뮬 검증 ✅

패널을 실제로 켤 경로인데 지금까지 합성만 통과하고 한 번도 돌려본 적이 없었다.
`-DPANEL_TEST=1`로 컴파일해 §1.5·1.6·1.9의 검사기로 검증했다.

```
sd_check: U=ff Z=0 D=0
line_dup: V=0 L=960
verdict:  pass=1 fail_code=0
PASS
```

`U=ff`는 구동 프레임에 박스(`2'b10` VPOS)와 배경(`2'b01` VNEG)이 둘 다 있기
때문이다. 예상 서명 그대로다.

`V=0`이 나온 것도 우연이 아니다. 데모 모드는 라인 복제를 쓰지 않고 `v_cnt_offset`을
패널 라인 좌표로 직접 쓰는데, 박스가 라인 600~999라서 **쌍 경계(600·1000 모두
짝수)와 정확히 맞아떨어진다.** 어긋났으면 경계 쌍에서 `V`가 튀었을 것이다.

**이걸로 패널 없이 가능한 FPGA 검증이 전부 소진됐다.**

### 1.13 ⚠️ XIAO의 I2C는 PMIC에 닿지 않는다 (회로도 확인)

plan.md §1.4가 "핀 대 핀 연결은 회로도를 눈으로 열어 확인할 것"이라고 남겨둔
부분을 실제로 열어봤다. 넷 이름 추론으로는 안 보이던 것이 나왔다.

| 시트 | 확인 내용 |
|---|---|
| 6 | TPS651851 U10 — 핀 17 `SCL` ← `ITE_I2C_SCL`, 핀 18 `SDA` ← `ITE_I2C_SDA` |
| 7 | IT8951 U12 — `I2C_SCL/SDA` → `ITE_I2C_SCL/SDA`, 풀업 R18/R19 4.7K |
| 5 | XIAO U3 — `GPIO41`→`IO41/I2C_SCL`, `GPIO42`→`IO42/I2C_SDA` → **SHT40(0x44)** |

**`ITE_I2C_*`와 `IO4x/I2C_*`는 서로 다른 넷이다.** PMIC의 I2C는 IT8951이
마스터인 버스에 있고, XIAO의 I2C에는 온습도 센서만 달려 있다.

즉 **이 스케치가 `0x68`로 보낸 I2C는 전부 허공으로 갔다.** 레지스터 주소와
계산식을 고쳐도(커밋 3b4c3e6) 패킷이 PMIC에 도달하지 않으므로 효과가 없다.

plan.md의 **"`REG_ENABLE` 주소는 맞으므로 어떤 레일을 켤지는 제대로 전달된다"는
전제가 틀렸다.** 다만 "레일이 올라오는 공은 IT8951에 있다"는 결론은 더 확실해진다
— I2C가 닿지 않으니 IT8951 말고 레일을 올릴 주체가 없다.

**배선 계획이 바뀐다.** `WAKEUP`/`PWRUP` 2선만 XIAO로 끌어오면 되는 게 아니라
**I2C 2선도 함께** 끌어와야 한다. IT8951을 리셋에 붙잡으면 I2C 마스터도 같이
사라지기 때문이다. 테스트포인트가 있다:

```
ITE_I2C_SCL  TP2      ITE_I2C_SDA  TP3      PWR2_WAKEUP  TP57
```

> 배선 전에 `scan` 명령 한 번으로 확정된다. `0x44`만 나오고 `0x68`이 없으면
> 위 판독이 맞다. 렌더된 회로도를 읽은 결과이므로 반드시 실측할 것.

### 1.14 PMIC 해법 — IT8951을 시킨다 (배선 불필요)

§1.13에서 XIAO의 I2C가 PMIC에 닿지 않는 것이 확인됐지만, **XIAO는 IT8951과
SPI로 이미 연결돼 있다**(시트 5·7: `SPI0_CLK/MOSI/MISO/CS`). 그리고 IT8951이
바로 그 PMIC I2C 버스의 마스터다.

```
XIAO ──SPI──> IT8951 ──I2C──> TPS651851
```

Seeed_GFX가 이 경로를 이미 구현해 두었다:

```cpp
void TFT_eSPI::setTconVcom(TWord vcom) {
    tconWriteCmdCode(0x0039);   // IT8951 VCOM 명령
    tconWirteData(0x02);        // 0x02 = write
    tconWirteData(vcom);        // mV 단위 (양수 크기)
}
```

`getTconVcom()`으로 **읽기까지 된다** — 멀티미터 없이 현재 VCOM을 확인할 수 있다.

**제어권을 뺏는 대신 IT8951을 시키면 납땜이 전혀 필요 없다.** plan.md §1.4의
"IT8951을 리셋에 붙잡음 (권장)"이 이걸로 뒤집힌다. A안과도 충돌하지 않는다 —
패널 FPC를 EE03에 안 꽂으므로 IT8951 출력은 아무 데도 안 가고, 전원 7선만 나간다.

**구현: 원래 `xiao_pmic_controller/ee03_rails/`에 있었고, 지금은 `xiao_pmic/`로 정리됨.**

| 항목 | 내용 |
|---|---|
| 기반 | Seeed_GFX `examples/ePaper/Basic/ED115OC1_Test` |
| 클래스 | `TFT_eSPI` 직접 사용 — `EPaper`는 생성자가 2760×2070 스프라이트를 할당한다 |
| **VCOM** | `hostTconInit()`의 하드코딩 `1400`(−1.40 V)을 **`1310`(−1.31 V)** 로 덮어씀 |
| 추가 제어 | `PIN_PWR_SW`(GPIO6) LOW — EE03 메인 전원 게이트. 라이브러리가 안 건드린다 |
| 명령 | `info` `vcom <mV>` `sleep` `wake` `help` |
| 빌드 | `arduino-cli compile --fqbn esp32:esp32:XIAO_ESP32S3:PSRAM=opi xiao_pmic` |

> `setTconVcom(1400)`은 Seeed_GFX가 10.3인치 패널용으로 쓴 값이다. 90 mV 차이는
> 대비 저하와 잔상으로 나타난다.

### 1.15 ⚠️ IT8951 최종 사망 확정 (2026-08-25) — **이 절의 결론은 틀렸다**

> ⛔ **2026-09-04 철회.** IT8951은 죽지 않았다. 이 절이 소진했다고 적은 "모든
> 경로"는 전부 같은 결함을 공유하고 있었다 — read preamble 뒤에 HRDY를
> 기다리지 않는 것. §1.19 참고. 아래 기록은 그때의 판단 과정으로 남긴다.


§1.14의 해법(IT8951을 통한 SPI 제어)을 실기로 시도한 결과, IT8951 자체가
응답하지 않는다는 것이 밝혀졌다. `ED115OC1_Test`(Seeed_GFX 공식 예제)를 그대로
올려도 동일 — `panel geometry 0x0`, `FW/LUT` 문자열 공백, `VCOM readback 0`.
라이브러리를 완전히 우회하고 원인을 좁혔다.

| 시도 | 결과 |
|---|---|
| 전원 레일 전부 실측 (`VCC_3V3`/`VD_1V8`/`VCC_ITE_3V3`) | 전부 정상 |
| `MISO` 직렬저항(`R9`) 실장 확인 | 정상 — 단선 아님 |
| **Raw SPI로 라이브러리 우회**, `Tcon.cpp` 그대로 재현한 프로토콜, 클럭 6종(0.1~10MHz) | 커맨드 전송·버스트 읽기 완주(HRDY ok)되지만 응답 데이터 **항상 0** |
| `HRDY` 관찰 (고정 딜레이 대신 최대 10초 폴링) | 리셋 해제 후 **정확히 1601ms**에 HIGH — 전원 안정화와 무관한 IT8951 내부 고정 타이머로 보임 |
| IT8951 데이터시트 Power-On Sequence 반영 — 전원 안정화 시간 50ms→**1000ms**로 20배 증가 | 결과 완전 동일 (`HRDY` 타이밍까지 똑같이 1601ms) — 전원 시퀀싱 가설도 배제됨 |

**결론: IT8951(TCON)은 사망 확정.** 소프트웨어·타이밍으로 시도 가능한 모든
경로를 소진했다. 전원·배선·MISO 저항 전부 정상인데 칩이 응답하지 않으므로,
남은 설명은 칩 내부(코어 또는 부팅용 펌웨어) 고장뿐이다.

**깃 히스토리로 미스터리도 풀렸다.** "예전에 전압이 나왔다"는 기억은 코드가
한 일이 아니라, 그때 IT8951이 살아서 `TFT_RST` 리셋만으로 **자체적으로**
`WAKEUP`/`PWRUP`을 구동해줬기 때문이었다(§6.4 파워온 시퀀스 원문: *"WAKEUP
pin is pulled high with PWRUP pin high... rails come up"*, 그리고 IT8951이
이 두 핀의 GPIO를 쥐고 있다). 깃 로그의 최초 버전(`2463af0`)이 `WAKEUP`/`PWRUP`을
XIAO GPIO로 직접 구동하려 시도했었는데 — "기판 그대로"였다는 확인으로 그
배선은 실제로는 연결된 적이 없었다는 것도 확정됐다. 즉 배선 없이 되던 유일한
경로가 IT8951 경유였고, 그게 끊겼다.

**결정: 새 EE03 보드 구매.** 이 보드는 폐기하지 않는다 — 전원부·테스트포인트는
멀쩡하니 예비 부품이나 배선 실험용으로 남긴다.

### 1.16 ~~새 EE03용 4선 배선 계획~~ — **폐기** (2026-09-07)

§1.19에서 IT8951이 살아 있는 것으로 밝혀지면서 이 계획의 전제(“TCON이 죽었으니
외부 MCU가 PMIC를 직접 잡는다”)가 사라졌다. **실행하지 않는다.** RP2040-Zero도
필요 없다.

폐기하면서 한 가지가 드러났으니 남겨둔다 — **이 표는 틀려 있었다.**

| 계획했던 것 | 실제 (회로도 7페이지) |
|---|---|
| `ITE_I2C_SCL` → `TP42` | 맞음 |
| `ITE_I2C_SDA` → `TP43` | 맞음 |
| `WAKEUP` → **`TP57`** | **틀림.** `TP57`은 IT8951 63번 `GPIO9/PWR1`이고 테스트포인트 외에는 아무 데도 안 간다. `WAKEUP`은 `PWR2` = 64번 `GPIO10`이며 **테스트포인트가 없다.** 그대로 납땜했으면 엉뚱한 핀에 물렸을 것 |

또한 “`PWRUP`은 배선 불필요”라고 적어둔 것도 오해를 부른다. EE03에서 `PWRUP`은
이미 IT8951 66번(`GPIO12/PWR4`)에 `R123`/`R110`(둘 다 0R, 실장)로 **직결돼
있다.** `ENABLE`(0x01)의 `ACTIVE` 비트로 대체 가능하다는 것은 외부 MCU를 쓸
때의 이야기였다.

> **지금 유효한 결론.** PMIC 파워업은 I2C가 아니라 전용 핀(`WAKEUP`/`PWRUP`)이
> 하고, 그 핀들은 IT8951에 직결돼 있다. IT8951이 호스트에 노출하는 명령 중
> PMIC를 건드리는 것은 `VCOM`(0x0039) 하나뿐이며 I2C 패스스루는 없다. 임의
> 레지스터를 쓰려면 IT8951 내부 I2C 마스터를 `REG_WR`로 몰아야 하는데 그
> 레지스터 블록은 공개 맵에 없다. **따라서 레일을 올리는 길은 `DPY_AREA`로
> TCON에게 리프레시를 시키는 것뿐이다** (§1.21).

### 1.17 BTN2 니블 리드아웃 (보조 — 이제 거의 쓸 일 없음)

BTN2 홀드 중 LED 6개가 `E` 필드(오차)를 16진 니블로 순환 표시한다.
인덱스 2비트 + 값 4비트 = LED 6개를 전부 쓴다. **점등 = 논리 1**
(`debug_ctrl`이 `~diag`로 반전해 active-low LED를 직접 구동).
정상이면 네 니블 모두 0. UART가 있으면 UART를 쓸 것.

### 1.18 EE03 / 패널 40P 커넥터 핀맵 확정 (2026-08-25)

브레이크아웃 배선 전에 두 커넥터의 핀맵을 문서로 확정했다.

- **EE03 J1**(AFC24-S40FIA-00): 회로도 PDF
  (`XIAO_ePaper_Display_Board_EE03_V1.0_SCH_251217.pdf`, 6페이지) 텍스트 레이어를

  위와 동일하되 **36=+VP(+15V) / 37=NC**, 그리고 **40은 BORDER가 아니라 −VCOM에
  결선**. plan.md §1.2가 40=BORDER로 적고 있었던 것은 오류 — 수정 완료.
- **결론(정정본)**: 36/37을 바로잡고 나면 두 보드의 전원 핀맵은 **일치한다.**
  EE03에서 VGL(1)·VGH(3)·+3V3(5,11)·GND(9,12,22)·VCOM(10)·**+15V(36)**·−15V(38)을
  탭해 패널 맵의 **같은 번호**에 꽂는다. 36↔37 크로스오버는 필요 없다.
  34번(TEST)은 GND가 아니므로 접지선으로 쓰지 말 것.
- README(FPGA↔PMOD 핀맵)는 `gowin_constraints.cst`와 대조해 오류 없음을 확인했다.

### 1.19 ✅ IT8951은 살아 있었다 — HRDY 게이팅 누락 (2026-09-04)

새 EE03가 도착해 확인해보니 **똑같이 0을 반환했다.** 두 개체가 동일하게
실패하면 개체 불량이 아니다. 결정적 단서는 §1.15가 이미 적어둔 숫자였다:

> `HRDY`는 리셋 해제 후 **정확히 1601ms**에 HIGH

새 보드는 **1605ms**. 죽은 칩이 서로 다른 두 보드에서 같은 시각에 재현성 있게
핀을 놓아줄 리 없다. 그건 정상 부팅의 서명이었지 고장의 서명이 아니었다.

**진짜 원인: read preamble(`0x1000`)을 보낸 뒤 HRDY를 기다리지 않았다.**
IT8951은 전송의 매 단계마다 호스트가 준비 신호를 확인하기를 요구한다.
`xiao_pmic`의 비트뱅 코드도, 라이브러리 경유 경로도 이 대기를 건너뛰고 있었다.
실측된 대기 시간은 **최대 30ms** — 고정 딜레이로는 절대 못 맞출 값이다.

대기를 넣자 즉시 답이 나왔다 (`ee03_probe`의 `tcon2`, 3회 재현):

```
raw: 0750 057C BE78 003D 5365 6565 645F 762E ...
panel W: 1872   panel H: 1404
FW version: 'Seeed_v.0.1'
LUT version: '3M29T'
HRDY waits honoured: 5, longest 30 ms
```

**PMIC도 열렸다** (`pmic2`, VCOM 5회 연속 동일):

```
read 1..5: 2500   -> -2.50 V
```

즉 §1.14의 "IT8951을 시켜서 PMIC를 제어한다"는 경로는 **막힌 적이 없었다.**
§1.16의 4선 배선(TP42/TP43/TP57/R129)은 이제 필수가 아니라 예비책이다.

> ⚠️ **판독 시 주의.** 게이팅 없는 읽기는 0만 주는 게 아니라 **그럴듯한 쓰레기**를
> 준다. 첫 시도에서 VCOM이 `1404`(패널 기본값 1400과 흡사)로 나와 잠깐 성공으로
> 오판했는데, 순서를 바꿔 다시 읽으니 `61`이었다. 구동되지 않는 MISO의 노이즈다.
> **한 번 읽고 믿지 말 것** — 값이 그럴듯할수록 더 그렇다.

**남은 불일치 두 가지 (해결 안 됨):**
- `panel W/H = 1872 x 1404`. 이 프로젝트 패널은 **2760 x 2070**이다. TCON에
  플래시된 패널 프로파일이 Seeed 키트용(10.3")이라는 뜻으로 보이는데,
  FPGA가 패널을 몰 것이므로 문제는 아니다. 다만 `driver.h`의 해상도
  오버라이드가 무엇을 덮어쓰고 있는지는 다시 봐야 한다.
- `VCOM = -2.50 V`. 패널 라벨은 **-1.31 V**. 붙이기 전에 반드시 고쳐야 한다.

### 1.20 VCOM은 휘발성이다 — XIAO가 최종 구성에 남는다 (2026-09-04)

§1.19로 PMIC 경로가 열린 뒤, VCOM 쓰기가 전원을 넘겨 살아남는지 시험했다
(`ee03_probe`의 `vtest`). PMIC의 `PROG` 비트는 건드리지 않았다 — 굽는 횟수가
제한된 비가역 동작이고, 여기서 필요하지 않다.

```
[1] 현재값                    2500 mV
[2] 1310 쓰기 → 되읽기        1310 mV   -- 쓰기는 먹는다
[3] TFT_ENABLE LOW, 3초
[4] 레일 복구 + TCON 리셋     HRDY 1605 ms
[5] 다시 읽기                 2500 mV   -- 되돌아갔다
```

**결론: 휘발성.** 그리고 값이 아무 데나로 간 게 아니라 정확히 `2500`으로
돌아왔다 — 부팅할 때 무언가가 이 값을 다시 써준다는 뜻이다. PMIC의 파워온
기본값인지 IT8951이 자기 설정을 PMIC에 복원하는 것인지는 아직 구분 못 했다.
어느 쪽이든 실무적 결론은 같다.

> **설계 영향.** EE03 위의 XIAO는 전원 게이팅(`PWR_EN`)만 하는 부품이 아니라
> **매 파워업마다 VCOM을 1310으로 써주는 역할로 최종 시스템에 남아야 한다.**
> §1.16이 상정한 "RP2040이 PMIC를 맡고 XIAO는 전원만"이라는 그림과 다르다.
> 4선 배선을 하지 않는 한, VCOM은 XIAO→IT8951→PMIC 경로로만 설정된다.

> ⚠️ 이 시험은 `TFT_ENABLE`(로직 레일)만 내렸다. 보드 입력 전원을 완전히
> 뽑는 쪽이 더 강한 시험이고, 아직 안 해봤다.

⛔ **패널 연결 전 필수.** 현재 기본값 `-2.50 V`는 패널 라벨 `-1.31 V`보다 훨씬
세다. 패널을 붙이기 전에 반드시 VCOM을 먼저 세팅할 것.

### 1.21 `PWR_EN`은 PMIC의 입력 전원까지 켠다 / 레일 시도 (2026-09-07)

레일을 올리려고 `ee03_probe`에 `rails` 명령을 넣으면서 회로도를 다시 읽었고,
그 과정에서 지금까지 놓치고 있던 게이팅이 하나 나왔다.

**`EDP_Drive`(= TPS65185의 `VIN`, 10번)는 VSYS 직결이 아니다.**

```
VSYS --> U18 (TPS22916C 로드스위치, EN = PWR_EN) --> EDP_Drive --> PMIC VIN
          \_ 우회 0R은 DNP -- 대체 경로 없음
```

그리고 `PWR_EN`은 XIAO 커넥터 7번 `U0TXD_D6` = **GPIO43**, 즉 `driver.h`의
`TFT_ENABLE`과 같은 핀이다. 핀 하나가 로직 레귤레이터(`R158` 0R → EN, 100K
풀다운)와 PMIC 입력 로드스위치를 **동시에** 켠다.

> §1.16이 “`TFT_ENABLE`은 로직 레일만 켠다”고 적었던 것은 불완전했다.
> **PMIC의 `VIN`도 이 핀에 달려 있다.**

**PMIC 제어 경로는 전부 실장돼 있다** (0R, DNP 없음): `SCL`/`SDA`(R156/R157),
`WAKEUP`(R133+R105, 100K 풀다운), `PWRUP`(R123+R110),
`PWR_GOOD`(R150+R132, `VCC_ITE_3V3`에 10K 풀업), `VCOM_CTRL`(R96+R108).
IT8951 쪽은 62~69번의 `PWR0`~`PWR7` 블록.

**`rails` 명령의 결과 (재현 3회).**

```
[TCON] RESPONDS -- 1872 x 1404, FW 'Seeed_v.0.1', LUT '3M29T'
[PMIC] LINK OK  -- VCOM reads 2500 mV (5 agreeing reads)
[TCON] SYS_RUN accepted
[TCON] I80CPCR = 1 (packed write enabled)
[TCON] DPY_AREA #1: command accepted, 5 args sent, refreshing
[TCON] DPY_AREA #1: LUTAFSR reads idle
[TCON] DPY_AREA #2: command accepted, HRDY still low   <- 이후 영구 대기
```

1차 리프레시는 인자까지 완주하고, 2차에서 HRDY가 내려간 채 돌아오지 않는다
(15초를 줘도 동일). `LUTAFSR`(0x1224)가 즉시 idle을 반환하는 것으로 보아 이
펌웨어에서 그 주소는 busy 플래그가 아니며, 아직 도는 엔진에 다음 명령을 밀어
넣어 wedge된 것으로 보인다.

**이 stall은 `PWR_GOOD`을 영원히 기다리는 모습과도 정확히 일치한다.**
`PWR_GOOD`은 PMIC의 오픈드레인 출력이고 레일이 정상일 때만 HIGH가 된다.

⚠️ **주의해서 읽어야 할 함정.** PMIC는 `VIN3P3`(=`VCC_ITE_3V3`)만으로도 I2C에
응답한다. 즉 **`U18`이 안 열려 `VIN`이 0인데도 지금까지의 모든 소프트웨어 검사는
전부 통과한다** — VCOM 되읽기까지 포함해서. `[PMIC] LINK OK`는 “PMIC가 살아
있다”는 뜻이지 “레일을 만들 수 있다”는 뜻이 아니다.

**미해결 — 실측 1점이 갈림길이다.** `rails` 창 안에서 `TP22`(EDP_Drive) ↔ `TP41`(GND):
- **~5 V** → `U18` 통과. 입력은 있는데 레일이 안 나오는 것이므로 파워시퀀스 쪽.
- **0 V** → `U18` 미개방. stall의 완전한 설명이 되고, GPIO43 실측/`U18` 불량으로 좁혀진다.

**스케치 상태.** `ee03_probe`에 `rails [초]` 추가(기본 60초). 파일 상단의
`RAILS_ON_BOOT`가 1이면 부팅 시 자동 실행 — 리셋만 누르면 창이 열린다.
⛔ **패널을 J1에 연결하기 전에 반드시 0으로 되돌릴 것.** 1로 두면 매 리셋·매
USB 삽입마다 무인으로 고전압이 올라오고 패널 버스를 구동한다. VCOM은 사용자
결정으로 당분간 2500(−2.50 V) 유지.

## 2.5 빌드가 두 개인 이유

목표는 하나다 — **FPGA가 스스로 만든 영상으로 패널을 구동한다.** 빌드가 둘로
갈린 것은 설계 의도가 아니라 **DDR3가 없어서 생긴 결과**다.

```
make (일반)
  vin.v 패턴 → degamma → 디더링 → 웨이브폼 LUT → pixel_processing → 출력
                                                       ↕
                                                    VRAM (픽셀당 16비트 상태)

make demo (PANEL_TEST)
  박스 위치 비교 → 2비트 구동값 → 출력
```

`vin.v`의 체커보드·램프·줄무늬도 자체 생성 영상이 맞다. 차이는 **VRAM 의존**이다.

Caster의 저지연 핵심은 각 픽셀이 어디까지 구동됐는지 기억해 목표에 도달한
픽셀을 건너뛰는 것(early cancellation)이고, 그 상태가 픽셀당 16비트 · 총
2,457,600 바이트다. 지금 그 저장소가 128비트 레지스터 하나라서 파이프라인의
구동 판단이 무의미하다. 실제 관측:

```
하드웨어   U=ff 무한 지속    상태가 갱신 안 돼 영원히 구동
시뮬(스텁) U=00 즉시 정지    전 화면이 한 덩어리로 "완료" 판정
```

**BSRAM으로는 대체 불가.** GW2A-18은 46 × 18 kb ≈ 103 KB로 23배 부족하다.
담을 수 있는 것은 약 5만 픽셀(256×200 정도)이라 2560×1920 스캔 영역에는
의미가 없다. DDR3가 진짜로 필요한 이유다.

`PANEL_TEST`는 상태를 기억할 필요가 없다. 그림을 FPGA가 직접 만드니 모든
픽셀의 목표값을 이미 알고 매 사이클 전체를 다시 그리면 된다. 저지연 기법은
못 쓰지만 **배선·전원·타이밍·프레임레이트는 전부 그대로 검증된다.**

| | 지금 | DDR3 붙은 뒤 |
|---|---|---|
| `make demo` | ✅ 패널 점등 가능 | 계속 유효 (브링업용) |
| `make` | ⚠️ 구동은 하나 판단이 무의미 | ✅ 진짜 저지연 동작 |

**첫 점등은 `make demo`로 한다.** 결정적이고 Hi-Z를 출력할 수 없는 구조라
안전하다. 일반 빌드로도 뭔가 나오긴 하겠지만 통제된 시험이 아니다.

  버튼으로 모드 전환만 한다
